## Group 1: Object-Oriented Programming (OOP) Concepts

### Q1: How does SmartOPD demonstrate the Four Pillars of OOP?
SmartOPD models hospital operations using all four classical OOP pillars. **Abstraction** is established through base classes like `Person` and `Patient`, which hide complex demographic and triage details behind clean interfaces. **Inheritance** allows clinical subclasses (`EmergencyPatient`, `ScheduledPatient`, `WalkInPatient`) and `Doctor` to inherit shared traits and methods from `Patient` and `Person`. **Polymorphism** enables `SmartOpdStrategy` to compute priority scores dynamically by invoking overridden methods like `urgencyBonus()` without checking concrete types. Finally, **Encapsulation** protects algorithmic invariants inside `Settings` and `DoctorQueue`, keeping state private and accessible only via validated mutators.  
**Show:** `backend/src/main/java/com/smartopd/model/Patient.java` and `backend/src/main/java/com/smartopd/model/Person.java`

### Q2: How is Dynamic Polymorphism implemented without using `instanceof` checks?
In SmartOPD, priority score evaluation completely avoids type-checking anti-patterns like `if (p instanceof EmergencyPatient)`. Instead, the abstract class `Patient` declares two abstract methods: `urgencyBonus(Instant now)` and `fairnessThresholdMinutes(Settings settings)`. Each concrete subclass provides its own polymorphic implementation: `ScheduledPatient` computes time-to-slot urgency, while `WalkInPatient` returns `0.0`. When `SmartOpdStrategy.calculateScore()` executes, the Java Virtual Machine dynamically dispatches to the subclass implementation at runtime based on the actual object instance.  
**Show:** `backend/src/main/java/com/smartopd/scoring/SmartOpdStrategy.java` in `calculateScore()`

### Q3: What is the Strategy Design Pattern, and where is it applied in SmartOPD?
The Strategy pattern is a behavioral design pattern that defines a family of interchangeable algorithms, encapsulates each one, and makes them interchangeable at runtime. SmartOPD defines the `PriorityStrategy` interface with three concrete strategies: `FcfsStrategy` (pure arrival order), `StrictPriorityStrategy` (clinical severity dominant), and `SmartOpdStrategy` (aging-aware anti-starvation triage). Crucially, the exact same strategy implementations are reused across both the live clinical queue (`DoctorQueue`) and the discrete-event simulator (`Simulator`), guaranteeing mathematical consistency across production and testing. Hospital administrators can dynamically hot-swap triage policies via `QueueManager.setStrategy()` without restarting the application.  
**Show:** `backend/src/main/java/com/smartopd/scoring/PriorityStrategy.java` and `backend/src/main/java/com/smartopd/scoring/SmartOpdStrategy.java`

### Q4: How does the Factory Design Pattern simplify patient creation and validation?
SmartOPD implements the Factory Method creational pattern via `PatientFactory.createPatient()`. This encapsulates the complex decision-making of instantiating the correct subclass (`EmergencyPatient`, `ScheduledPatient`, or `WalkInPatient`) away from controllers and services. Before object creation, the factory strictly validates business invariants: rejecting blank names, ensuring 10-digit phone formatting, enforcing that emergency patients possess Level 4 or 5 triage severity, and checking that the target doctor is not `OFF_DUTY`. If inputs are invalid, the factory fails fast with a `ValidationException` before any database sequence is consumed.  
**Show:** `backend/src/main/java/com/smartopd/model/PatientFactory.java` in `createPatient()`

### Q5: Why are Java 17 Records used for Data Transfer Objects (DTOs), and what OOP principle do they represent?
Java Records (introduced in Java 16/17) are used throughout the API layer for DTOs such as `LoginResponse`, `PatientRegisterRequest`, and `PublicTrackerResponse`. Records represent pure **Immutability and Value Objects**, automatically generating `final` fields, canonical constructors, `equals()`, `hashCode()`, and `toString()`. This prevents accidental state corruption between the HTTP controller boundary and the service layer. By decoupling external JSON payloads from internal mutable domain entities like `Patient`, records enforce strict encapsulation and defend against mass-assignment security vulnerabilities.  
**Show:** `backend/src/main/java/com/smartopd/api/dto/PublicTrackerResponse.java`

### Q6: How does the DAO (Data Access Object) pattern decouple domain business logic from the database?
The DAO pattern abstracts and encapsulates all access to the SQLite data source. Interfaces like `PatientDao`, `DoctorDao`, and `EventDao` declare high-level business contracts (e.g., `findWaitingByDoctor()`), while concrete classes like `JdbcPatientDao` contain raw JDBC queries, connection handling, and result set mapping. Because `QueueService` interacts only with DAO interfaces, the entire underlying database engine could be migrated from SQLite to PostgreSQL without altering a single line of triage scoring or queue management logic. This strictly adheres to the Dependency Inversion Principle (DIP).  
**Show:** `backend/src/main/java/com/smartopd/dao/PatientDao.java` and `backend/src/main/java/com/smartopd/dao/jdbc/JdbcPatientDao.java`

### Q7: How does the system enforce class invariants, and why are defensive copies used?
Class invariants are conditions that must always remain true for an object throughout its lifecycle. SmartOPD enforces invariants in constructors and setters: `Person.setAge()` throws `ValidationException` if age is not between 1 and 130, while `Doctor.setAvgConsultMinutes()` clamps durations between 3 and 60 minutes. Furthermore, `Settings.copy()` implements defensive copying. When the simulation engine runs 90 benchmarking iterations or when settings are temporarily updated, defensive copies ensure that background calculations cannot mutate the live hospital's active triage parameters.  
**Show:** `backend/src/main/java/com/smartopd/config/Settings.java` in `copy()` and setters

### Q8: Where are Java Generics used in SmartOPD, and what problem do they solve?
Generics provide compile-time type safety and eliminate hazardous runtime type casting. In SmartOPD, generics are applied in `TransactionHelper.execute(TransactionCallback<T>)`. The callback interface declares `T doInTransaction(Connection conn) throws SQLException`, allowing any service method to return arbitrary entity types—such as `RegistrationResult`, `Patient`, or `Optional<UserAccount>`—through a unified transactional wrapper. Generics ensure that the calling code receives strongly-typed results without needing unsafe `(Patient)` casts.  
**Show:** `backend/src/main/java/com/smartopd/dao/TransactionHelper.java` in `execute()`

## Group 2: Algorithm & Fairness

### Q9: What is the SmartOPD mathematical scoring formula, and what role does each term play?
SmartOPD ranks waiting patients dynamically using the formula:  
$$\text{Score} = (\text{Severity} \times W_{\text{sev}}) + (\text{WaitMinutes} \times W_{\text{wait}}) + \text{UrgencyBonus} + \text{FairnessBoost}$$  
By default, $W_{\text{sev}} = 100.0$ and $W_{\text{wait}} = 3.0$, meaning clinical severity dominates initial placement (~33 minutes of waiting equates to climbing one triage tier). `UrgencyBonus` is calculated polymorphically for scheduled appointments as they near their booked slot (up to +60 points). `FairnessBoost` injects a flat $+150.0$ bonus once a patient's wait exceeds their category threshold (45 minutes). Critical Level 5 emergencies bypass scoring entirely with an override score of $10,000.0$.  
**Show:** `backend/src/main/java/com/smartopd/scoring/SmartOpdStrategy.java` in `calculateScore()`

### Q10: Why is the average overall waiting time virtually identical between FCFS, Strict Priority, and SmartOPD?
According to queuing theory (specifically Little's Law: $L = \lambda W$), when arrival rates, service durations, and doctor capacities are identical, **the total work in the system is conserved regardless of work-conserving dispatching order**. As proven by our 30-seed simulation report, overall average wait is conserved across all policies. What SmartOPD changes is not the total waiting time, but **who bears that wait**. It redistributes delays from vulnerable, life-threatening emergency cases to less critical patients while enforcing strict aging bounds so scheduled appointments do not suffer unbounded starvation.  
**Show:** `backend/src/main/java/com/smartopd/simulation/SimulationReport.java` and `docs/VIVA.md` benchmark table

### Q11: What is the "trade-off" or cost to routine walk-in patients under the SmartOPD policy?
The trade-off in SmartOPD is that routine walk-in patients (Severity Level 1 or 2) wait slightly longer on average to protect critical patients and scheduled appointment promises. In our 30-seed benchmark, walk-in waiting times averaged $6.74\text{m}$ under pure FCFS, increasing to $10.32\text{m}$ under SmartOPD. This ~3.5 minute increase is the conscious, transparent clinical trade-off required to drop emergency waiting times from $6.86\text{m}$ down to $1.27\text{m}$ and eliminate scheduled patient starvation entirely.  
**Show:** `backend/src/main/java/com/smartopd/simulation/Simulator.java` in `generateInsights()`

### Q12: How is clinical triage severity assigned to patients in SmartOPD? Is it computed by an AI algorithm?
Severity is **never assigned by an automated black-box algorithm**. In clinical reality, medical triage requires human clinical judgment. At SmartOPD registration, a trained front-desk nurse or triage officer assesses vital signs and assigns an explicit clinical tier from Level 1 (Routine/Minor) to Level 5 (Resuscitation/Immediate Life Threat) based on hospital triage protocols. The software's role is strictly explainable queue management and anti-starvation scheduling, not automated diagnosis.  
**Show:** `backend/src/main/java/com/smartopd/model/PatientRegistrationRequest.java` and `register-patient.html`

### Q13: What is the Emergency Cap rule (`MAX_CONSECUTIVE_EMERGENCIES = 2`), and how does it prevent starvation?
Under pure strict priority, during mass-casualty surges or emergency clusters, non-emergency patients can be delayed indefinitely. The Emergency Cap rule (`MAX_CONSECUTIVE_EMERGENCIES = 2`) solves this. If a doctor consults two emergency patients consecutively, the next call bypasses incoming Level 4 emergencies to consult the longest-waiting fairness-boosted patient. However, if an incoming patient is Level 5 (immediate life threat), the cap rule safely yields, ensuring clinical safety is never compromised.  
**Show:** `backend/src/main/java/com/smartopd/queue/EmergencyCapSelector.java` in `selectNextPatient()`

### Q14: How does the Anti-Starvation Fairness Boost work, and how does advancing the simulated clock trigger it?
When a patient waits in the queue, their elapsed waiting time is tracked against their category threshold (45 minutes for Scheduled and Walk-in). Once elapsed wait crosses 45 minutes, `isFairnessBoosted()` returns `true`, awarding $+150.0$ bonus points. In `QueueManager.advanceClock()`, advancing simulated time recalculates waits across all doctor queues. Any patient newly crossing the threshold is awarded the boost, an audit event (`FAIRNESS_BOOST`) is appended to `queue_event`, and the queue is re-sorted, visibly advancing the patient ahead of newer routine arrivals.  
**Show:** `backend/src/main/java/com/smartopd/queue/QueueManager.java` in `advanceClock()`

### Q15: What does "starvation" specifically mean in the discrete-event policy simulator?
In the SmartOPD simulation engine, "starvation" has a formal mathematical definition: **a scheduled appointment patient whose total queue wait time exceeds twice the scheduled fairness threshold** ($2 \times 45 = 90\text{ minutes}$). Under Strict Priority, starvation occurs regularly (0.44 patients per run in our benchmark) because unscheduled emergencies continuously cut in line. SmartOPD completely eliminates scheduled starvation ($0.00$ occurrences across all 90 runs).  
**Show:** `backend/src/main/java/com/smartopd/simulation/Simulator.java` in `simulatePolicy()`

## Group 3: Database & Transactions

### Q16: Why did you choose SQLite for this project, and how do you handle its single-writer limitation?
SQLite was chosen because it provides full ACID persistence with zero complex server setup, running as a lightweight C-library embedded within the JVM via JDBC. However, SQLite employs file-based locking where only one active writer thread is permitted at a time. To completely avoid `SQLITE_BUSY` lock contention across concurrent Spring Boot HTTP threads, SmartOPD serializes all mutating operations in `QueueService` through a single, fair `ReentrantLock(true)`. Readers execute non-blocking queries concurrently via Write-Ahead Logging (WAL mode).  
**Show:** `backend/src/main/java/com/smartopd/service/QueueService.java` in `writeLock` declaration

### Q17: How does `TransactionHelper` guarantee ACID properties and prevent dirty reads or orphaned records?
`TransactionHelper.execute()` manages JDBC connections using a functional template callback. It disables auto-commit (`conn.setAutoCommit(false)`), executes all related SQL inserts (token increment, patient creation, audit event logs), and commits them as a single atomic unit of work (`conn.commit()`). If any SQL statement fails or throws an exception, the `catch` block immediately invokes `conn.rollback()`. This guarantees that partial operations—such as incrementing a token number without successfully inserting the patient—can never occur.  
**Show:** `backend/src/main/java/com/smartopd/dao/TransactionHelper.java` in `execute()`

### Q18: What happens if an unexpected database error occurs mid-transaction during patient registration?
If a disk failure or constraint violation occurs mid-transaction, `TransactionHelper` rolls back the SQLite transaction. Immediately following this, `QueueService.registerPatient()` catches the exception and executes `rebuildDoctorQueueFromDb()`. This method re-reads all committed waiting patients and audit logs from SQLite, discarding any speculative in-memory queue changes and restoring in-memory state to match the database perfectly. Finally, `GlobalExceptionHandler` masks the error and returns a clean HTTP 500 JSON response without leaking database internals.  
**Show:** `backend/src/main/java/com/smartopd/service/QueueService.java` in `registerPatient()` catch block

### Q19: What happens to active queues, tokens, and consultation timers if the SmartOPD server crashes or restarts?
Because SmartOPD implements **write-through persistence**, zero data is lost. During startup, `QueueService` invokes `reloadAllFromDatabase()`. It reconstructs doctor queues from the `patient` table (restoring patients with status `WAITING` and `IN_CONSULTATION`), reloads token sequence counters from `token_sequence`, retrieves stored settings from `settings`, and restores simulated clock offsets from `app_state`. When the server comes back online, doctor queues, token sequences, and consultation timers resume seamlessly.  
**Show:** `backend/src/main/java/com/smartopd/service/QueueService.java` in `reloadAllFromDatabase()`

### Q20: Why does SQLite require Write-Ahead Logging (WAL) and foreign key activation in `ConnectionProvider`?
By default, SQLite disables relational foreign key enforcement and uses traditional rollback journals that lock the entire database file during writes. In `ConnectionProvider.getConnection()`, SmartOPD executes three critical PRAGMA statements on every newly acquired connection: `PRAGMA foreign_keys = ON;` (ensures referential integrity between patients and doctors), `PRAGMA journal_mode = WAL;` (enables Write-Ahead Logging so concurrent readers do not block on writers), and `PRAGMA busy_timeout = 5000;` (waits up to 5 seconds before throwing a busy error).  
**Show:** `backend/src/main/java/com/smartopd/dao/ConnectionProvider.java` in `getConnection()`

## Group 4: API, Security & Privacy

### Q21: How does SmartOPD authenticate staff users, and why aren't plaintext passwords stored?
SmartOPD implements defense-in-depth credential security in `PasswordHasher.java`. Passwords are never stored in plaintext or weak hashes like MD5. Instead, SmartOPD uses **PBKDF2WithHmacSHA256 with 120,000 hash iterations and 16-byte cryptographically secure random salts**. When a user logs in, the stored salt and input password are fed through PBKDF2; authentication succeeds only if the resulting hex digest matches the stored hash via a constant-time equality check, protecting against timing attacks.  
**Show:** `backend/src/main/java/com/smartopd/auth/PasswordHasher.java` in `verifyPassword()`

### Q22: How does the system implement Role-Based Access Control (RBAC) between Receptionists and Doctors?
Authorization is enforced declaratively using the `@RequiresRole` annotation and `AuthInterceptor`. When an HTTP request enters Spring Boot, `AuthInterceptor.preHandle()` extracts the bearer token, retrieves the active `UserSession` from `SessionStore`, and checks the controller's role requirements. If a doctor attempts front-desk tasks (e.g., patient registration or settings configuration), the interceptor immediately rejects the request with HTTP 403 Forbidden. Furthermore, doctors are cross-checked so they cannot access or mutate queues belonging to another doctor.  
**Show:** `backend/src/main/java/com/smartopd/api/security/AuthInterceptor.java` in `preHandle()`

### Q23: What brute-force protection mechanisms are implemented in `AuthController` and `SessionStore`?
To protect against automated credential guessing, `SessionStore` tracks failed authentication attempts per username in a sliding 5-minute window. If 5 consecutive failed attempts occur for any account, `SessionStore` locks the account for 60 seconds and throws `AccountLockedException`. Any subsequent login attempt (including the 6th attempt) is rejected immediately with HTTP 429 Too Many Requests without executing the CPU-intensive PBKDF2 hashing algorithm.  
**Show:** `backend/src/main/java/com/smartopd/api/security/SessionStore.java` in `recordFailedAttempt()`

### Q24: How does SmartOPD adhere to "Privacy by Design" on public display boards and patient tracker endpoints?
Public endpoints (`/api/public/board` and `/api/public/tracker/{token}`) are accessible without authentication, requiring strict privacy protection. SmartOPD enforces a **Zero-PII Rule**: responses never expose patient full names, mobile phone numbers, ages, genders, medical chief complaints, or clinical severity numbers. The waiting room display board displays only anonymous tokens (e.g., `CARD-E-002`) and doctor room numbers. The mobile tracker greeting displays only the patient's first name for identity verification.  
**Show:** `backend/src/main/java/com/smartopd/api/dto/PublicTrackerResponse.java` and `PublicController.java`

### Q25: What rate-limiting defenses exist on public tracking endpoints to prevent token enumeration?
Because patient queue tokens follow sequential departmental patterns (e.g. `CARD-W-005`, `CARD-W-006`), malicious actors could attempt to harvest queue statuses through enumeration. To prevent this, `PublicTrackerRateLimiter.java` maintains an in-memory sliding-window request tracker keyed by client IP address. Any client IP that exceeds 30 requests within a 60-second window on `/api/public/tracker/**` is throttled with HTTP 429 Too Many Requests.  
**Show:** `backend/src/main/java/com/smartopd/api/security/PublicTrackerRateLimiter.java` in `isAllowed()`

## Group 5: Testing, Simulation & Limitations

### Q26: How do the Java and JavaScript simulation engines achieve bit-exact parity, and how is that proven?
The discrete-event simulator was initially developed in JavaScript (`simulator.js`) as an executable specification and then ported to pure Java (`Simulator.java`). To guarantee identical patient cohorts across both languages, both engines implement the exact same **Mulberry32 32-bit pseudo-random number generator**. Bit-exact parity is mathematically verified by `SimulatorParityTest.java` across 9 golden benchmark suites (Quiet Day, Busy Day, Emergency Surge across seeds 1, 7, and 42), asserting that patient counts, average waits, and starvation counts match to the exact decimal place.  
**Show:** `backend/src/test/java/com/smartopd/SimulatorParityTest.java`

### Q27: What is Mulberry32, and why is it preferred over `java.util.Random` for discrete-event simulation?
Mulberry32 is a lightweight, high-quality 32-bit PRNG with a state period of $2^{32}$. Standard platform generators like `java.util.Random` (which uses a 48-bit Linear Congruential Generator) or browser-specific `Math.random()` cannot be synchronized across language runtimes. By implementing the exact Mulberry32 bit-shift and multiplication algorithm in both `frontend/js/simulator.js` and `backend/src/main/java/com/smartopd/simulation/SeededRandom.java`, we ensure that given seed 42, both runtimes generate the identical sequence of random numbers.  
**Show:** `backend/src/main/java/com/smartopd/simulation/SeededRandom.java` in `next()`

### Q28: What are the four automated test suites in SmartOPD, and what does each suite verify?
SmartOPD maintains four green automated test suites:
1. **Backend JUnit 5 Suite (`mvn test` - 84 tests):** Tests pure OOP domain classes, SQLite ACID transactions, multi-threaded concurrency, and simulation parity.
2. **Algorithm Verification Suite (`run-tests.js` - 48 checks):** Validates Mulberry32 PRNG, emergency override order, fairness aging boosts, and emergency cap rules in JavaScript.
3. **Static Decoupling Audit (`static-check.js` - 170 checks):** Scans all 10 HTML pages ensuring zero legacy mock leakage, correct script order, and strict REST API decoupling.
4. **REST API Contract Suite (`api-contract-test.js` - 141 checks):** Performs 15 live HTTP integration steps against the running server validating authentication, RBAC, and JSON DTO shapes.  
**Show:** `backend/src/test/java/com/smartopd/RestApiIntegrationTest.java` and `frontend/js/tests/api-contract-test.js`

### Q29: What are the real experimental results from running 90 simulated clinic sessions across seeds 1 to 30?
Running 90 simulated sessions over seeds 1 to 30 yields clear empirical proof of SmartOPD's efficacy:

- **Scheduled Starvation:** Under Strict Priority, starvation occurred at an average of $0.44$ patients per session (with maximum waits reaching $43.31\text{m}$). SmartOPD completely eliminated starvation ($0.00$ cases) and reduced maximum scheduled wait to $28.59\text{m}$.
- **Conserved Overall Work:** Overall average wait remained consistent across policies (~8 minutes), proving the queuing theory principle of work conservation.

### Q30: What limitations exist in this project, and what features are deliberately not implemented?
To maintain architectural focus as an educational OOP capstone project, several production features were intentionally omitted:
1. **Plain HTTP (No HTTPS):** Designed for localhost and private hospital Wi-Fi; TLS certificates should be terminated at a production reverse proxy (e.g. NGINX).
2. **In-Memory Sessions:** Bearer tokens are kept in `SessionStore` RAM; restarting the server invalidates active logins.
3. **Simulated Telephony:** Ticket SMS notifications and QR tracking links are rendered virtually on-screen rather than sending actual paid GSM SMS messages.
4. **Single-Writer Database:** SQLite allows only one writer; a high-volume multi-facility hospital network would replace SQLite with PostgreSQL or MySQL.  
**Show:** `docs/ARCHITECTURE.md` Section 3 and root `README.md`
